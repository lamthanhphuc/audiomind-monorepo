# Backup And Restore

This runbook covers MVP data preservation for the single-VPS production Docker
Compose deployment.

Production remains cloud-first:

- STT/transcription: Deepgram
- Analysis/summarization: Gemini
- Legacy Whisper/Ollama: not part of the default runtime path

Do not expose PostgreSQL, Redis, `ai-api`, or `celery-worker` publicly while
backing up or restoring data.

## Data To Preserve

Back up:

- PostgreSQL data from Compose service `db`.
- Uploaded audio and generated artifacts from Docker volume
  `audiomind-prod_uploads`.
- Backup manifest JSON generated by `backup-prod.sh`.

Usually optional:

- `job_status`, for in-flight or recent operational job state.

Usually skip for cloud-first MVP:

- `model_cache`
- `ollama_cache`

## Backup Directory

The production backup scripts default to:

```text
/opt/audiomind/backups
```

The scripts create this directory if needed, apply `chmod 750`, check available
disk before backup, and use retention cleanup for owned backup file patterns.
The directory must be on the VPS host filesystem, not inside a Docker volume.

Default retention is 14 days. `RETENTION_DAYS` must be at least 7 unless
`AUDIOMIND_BACKUP_FORCE_LOW_RETENTION=1` is set deliberately.

Disk preflight policy:

- Fail if available disk is below 2 GB.
- Warn if available disk is below 5 GB.

This matters on the current 40 GB SSD VPS.

## Run Backups

From the deployment checkout on the VPS:

```bash
cd /opt/audiomind/phase3-worktree
```

PostgreSQL only:

```bash
bash scripts/deploy/backup-postgres.sh
```

Uploads only:

```bash
bash scripts/deploy/backup-uploads.sh
```

PostgreSQL plus uploads plus manifest:

```bash
bash scripts/deploy/backup-prod.sh
```

The scripts:

- write backup artifacts to `.tmp` files first
- rename `.tmp` files to final names only after validation succeeds
- create `.sha256` files
- use `/tmp/audiomind-backup.lock` with `flock`
- avoid printing secrets
- do not mount or archive `infra/.env`

Expected filenames:

```text
audiomind-postgres-YYYYMMDDTHHMMSSZ.dump
audiomind-postgres-YYYYMMDDTHHMMSSZ.dump.sha256
audiomind-uploads-YYYYMMDDTHHMMSSZ.tar.gz
audiomind-uploads-YYYYMMDDTHHMMSSZ.tar.gz.sha256
audiomind-backup-manifest-YYYYMMDDTHHMMSSZ.json
```

## Validate Backups

List backup files and check sizes:

```bash
ls -lh /opt/audiomind/backups
test -s /opt/audiomind/backups/<postgres-backup>.dump
test -s /opt/audiomind/backups/<uploads-backup>.tar.gz
test -s /opt/audiomind/backups/<manifest>.json
```

Check disk:

```bash
df -h /opt/audiomind/backups
df -Pk /opt/audiomind/backups
```

Check SHA-256 files:

```bash
sha256sum -c /opt/audiomind/backups/<postgres-backup>.dump.sha256
sha256sum -c /opt/audiomind/backups/<uploads-backup>.tar.gz.sha256
```

List the uploads archive:

```bash
tar -tzf /opt/audiomind/backups/<uploads-backup>.tar.gz | head
```

Inspect the Postgres custom-format dump if `pg_restore` exists on the host:

```bash
pg_restore --list /opt/audiomind/backups/<postgres-backup>.dump | head
```

If `pg_restore` is not installed on the host, use the production Postgres major
version in a helper container:

```bash
docker run --rm \
  -v /opt/audiomind/backups:/backups:ro \
  postgres:15.7 \
  pg_restore --list /backups/<postgres-backup>.dump | head
```

Confirm the production uploads volume exists:

```bash
docker volume inspect audiomind-prod_uploads
```

## Download Backups To Local

Windows PowerShell:

```powershell
scp deploy@14.225.204.225:/opt/audiomind/backups/<backup-file> "$env:USERPROFILE\Downloads\"
scp deploy@14.225.204.225:/opt/audiomind/backups/<backup-file>.sha256 "$env:USERPROFILE\Downloads\"
scp deploy@14.225.204.225:/opt/audiomind/backups/<manifest>.json "$env:USERPROFILE\Downloads\"
```

Unix shell:

```bash
scp deploy@14.225.204.225:/opt/audiomind/backups/<backup-file> ~/Downloads/
scp deploy@14.225.204.225:/opt/audiomind/backups/<backup-file>.sha256 ~/Downloads/
scp deploy@14.225.204.225:/opt/audiomind/backups/<manifest>.json ~/Downloads/
```

Download both Postgres and uploads backups when preparing for disaster
recovery.

After downloading a backup and its `.sha256` file, verify from the local
download directory.

Unix shell:

```bash
cd ~/Downloads
sha256sum -c <backup-file>.sha256
```

Windows PowerShell with Git Bash, WSL, or another environment that provides
`sha256sum`:

```powershell
cd $env:USERPROFILE\Downloads
sha256sum -c .\<backup-file>.sha256
```

If `sha256sum` is not available on Windows, use WSL/Git Bash or compare the
hash manually with PowerShell:

```powershell
Get-FileHash .\<backup-file> -Algorithm SHA256
Get-Content .\<backup-file>.sha256
```

## Restore Dry-Run

Do not restore over production until:

1. A fresh backup has been created.
2. The backup files and checksums have been validated.
3. A dry-run inspection has passed.
4. The user has explicitly confirmed the destructive production restore.

Safe dry-run checks:

```bash
pg_restore --list /opt/audiomind/backups/<postgres-backup>.dump | head
tar -tzf /opt/audiomind/backups/<uploads-backup>.tar.gz | head
```

Host-independent Postgres validation:

```bash
docker run --rm \
  -v /opt/audiomind/backups:/backups:ro \
  postgres:15.7 \
  pg_restore --list /backups/<postgres-backup>.dump | head
```

Prefer restoring into a temporary test database/container before any production
restore.

## Restore Order

When a production restore is explicitly approved:

1. Take a fresh Postgres backup and uploads backup.
2. Stop app services that write data: `web`, `meeting-api`, `processing-api`,
   `user-api`, `ai-api`, and `celery-worker`.
3. Restore PostgreSQL from the approved custom-format dump.
4. Restore uploads only after deciding whether to merge or replace files.
5. Start services with the same production Compose files.
6. Run readiness checks.
7. Run the production smoke checklist.

For a destructive restore into an existing database, create a separate migration
plan first. Do not drop production data as an ad hoc rollback step.

## Upload Restore

Uploads restore must target the production volume only:

```text
audiomind-prod_uploads
```

If restoring over existing files, decide first whether to merge or clear the
target volume. Do not delete volume contents without a separate confirmation.

## Forbidden Commands

Never use these as part of backup, rollback, or routine restore:

```bash
docker compose down -v
docker volume prune
docker system prune --volumes
```

Do not delete Docker volumes as a shortcut.

## Backup Schedule

Suggested MVP minimum:

- Run `backup-prod.sh` before each deploy.
- Run `backup-prod.sh` daily for active demos.
- Review `/opt/audiomind/backups` disk usage weekly.

Systemd timer installation is intentionally out of scope for 7T-Ops-B1/B2/B3.

## Rollback Notes

Rollback should normally switch back to the previous compose/env/revision and
restart services without deleting volumes. Restore data only when the deploy
changed persisted data and a data rollback is explicitly required.
